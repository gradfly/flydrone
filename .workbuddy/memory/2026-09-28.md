### 关键发现：expL/expR 无法定位 looming 在哪一侧
- 原来打算用 `expL/expR`（每半侧 flow 的仿射斜率）判侧，实测**对着真实障碍物方位只有约 50–60% 一致**。原因是仿射斜率是整半侧拟合出来的"膨胀斜率"，对任何平滑膨胀场左右两半几乎相同，只有纹理加权在变——它测的是"膨胀多强"，不是"膨胀在哪"。
- 换成**每半侧纹理加权平均 divergence**（`div = ∂vx/∂x + ∂vy/∂y`，物理上 = 2·Vz/Z，正好"近的表面值大"）：两侧共同的地板/远墙在对比中相互抵消，只有近物体会把天平压向自己一侧，一致率升到 ~70–83%。
- 试过"每半侧取 max divergence"，**失败**：max 永远是地板，左右都有 → 所有 looming 都被判成 head-on climb（climb 占比 50%+，碰撞暴涨）。这个反例值得记住。
- 仍不完美：单次采样 3–5 个，样本量小时噪声大；`nearL/nearR` 量级只有 0.02–0.15，需要 0.5α EMA 平滑。

### A/B：loomFloor 0.15 vs 0.08（5 种子 ×45 s，6 障碍）
- 0.15 → 46 碰撞，高于 1.25 m 的时间占 5–18%
- 0.08 → 71 碰撞，高于 1.25 m 占 14–44%，逃逸次数 3 倍（21 vs 6）

### v15：looming 的 climb 改成概率门（用户反馈"climb 概率太高"）

问题：逃逸方向是查表（左近→右转 / 右近→左转 / 两侧接近→爬升），但**"两侧接近"的读数太常见**，实测 climb 占全部逃逸的 40%（29/72），每次都"边爬边飞 1.5 s"，飞行变成上下拉锯。

- `Decoder.escClimbP = 0.35`：head-on 读数只有 35% 真的爬升，其余降级成"朝略大那一侧转"（用 `sideEma` 的符号，仍是"背向膨胀侧"几何）。`escFromEye()` 本身不变（仍返回 climb）。
- `escHist` 增加 `climbDown` 计数（被门拦下的 head-on 读数），可从 `FD.state().escHist` 复查。
- 新增 `AUTO_TUNE.escClimbP`；applyTune 用 `Number.isFinite` 兜底。版本 v14 → v15。

6 种子 ×45 s（6 障碍）实测，门的行为精确符合配置（climbDown + climb = head-on 读数，climb 占比 ≈ escClimbP）：
- 1.00 → climb 占 40%，碰撞 43（3 种子口径）
- 0.35 → climb 占 17%，碰撞 6，接触时间 0%
- 0.20 → climb 占 10%，碰撞 43，接触 0.5%
- 0.10 → climb 占 4%，碰撞 39，接触 1.0%

结论：**降 climb 不是免费交换**。爬升会带来高度，纯转向不升高度，无人机长期留在障碍物高度层 → 碰撞/接触上升。0.35 是"climb 减半且不加碰撞"的点。碰撞数对参数高度混沌（同值换种子能差 20 倍），6 种子只是方向性证据，不是精确排序。

验证手法：纯 Node 内联跑 `Pilot`（不开浏览器），`node --input-type=module -e '...'`，3 配置 ×6 种子 ≈ 110 s。比 CDP 无头快得多，适合参数扫描。

### v17：修"碰到墙壁/障碍物悬停不动"（用户报的 bug）

诊断先行（这一步是关键）：写了个"停顿探测器"（速度 <0.10 m/s 持续 ≥0.5 s 记一次 episode），内置浏览器跑 6 种子 ×60 s。v15 结果：**23–50 次停顿 / 70.2 s 停顿（占 19.5% 飞行时间），最长 3.35 s**，而且
**几乎每次停顿 `touching` 都是 0%**——所以根本不是碰撞代码的问题。三个独立成因：

1. **geofence 死锁（墙边，最大头）**：`Safety.filter` 里 `if (r > 3.0 && forward > 0) forward = 0`，只看半径不看朝向。场地半宽 2.9 m，所以贴墙偏一点 r 就 >3；朝墙时 forward 被清零，朝场内时**同样**被清零；而 yaw 不改变半径 → 条件永远不解除 → 悬停。实测最长几次（1.35–3.35 s）全部 `geo:100%、rad≈3.1、touching=0%`。
2. **接触逃逸只转向不位移**：贴面时大脑持续命令 forward，`collide()` 恰好抵消掉朝里那一份 → 位置不变；只 yaw 不动 → 悬停。且 `Safety.slew_per_s=2.5` 让"forward 从巡航降到倒车"要 ~0.7 s，比逃逸本身（0.6 s）还长，光改指令值没用。
3. **大脑刹车把巡航清零（最隐蔽，与"碰到东西"无关）**：`raw.forward += cruise * max(0, 1 - brake)`，而 brake（DNp03）能 >1 → forward 直接归零，无人机在半空停 ~1 s（brake 是衰减峰值保持）。实测所有半空停顿的 brake 都是 0.6–2.4、touching=false，半径从 0.4 m（空地）到 2.9 m（障碍旁）都有——用户看到的就是"接近障碍物就悬停"。

修复（全部在 `engine.js`，参数在 `app.js` AUTO_TUNE）：
1. geofence 改为**只削掉朝外的那部分指令 + 把机头转向场地中心 + 侧向滑回场内**：`forward *= max(0, inward)`；`out.yaw -= clamp(err,-1,1)*0.8`（注意 SimDrone 是 `yrT = -c.yaw*yrMax`，正误差要负 yaw）；`out.lateral += inLat * max.lateral`（侧滑立刻有朝内分量，0.8 m/s <0.5 s 就能退出 0.3 m 的围栏带，不用等 1 s 转完 180°）。
2. 接触逃逸加**物理推离**：`SimDrone.pushOff(speed)` 直接把 `contactN`（collide 返回的法线）加到速度上，绕过 slew；`Decoder.pendingPush` 由 `Pilot.tick()` 消费。`contactCooldown` 2.0 → **0.9 s**（minifly.json 增 `escape.contact_s`）。
3. `Decoder.cruiseFloor`（默认 0，autoplay 0.4）：`raw.forward += cruise * max(cruiseFloor, 1 - brake)`。
4. `Pilot.stallBreaker()`：速度 <0.08 持续 1.0 s → 倒车 -0.6 + 转向 ±0.7，持续 0.7 s，左右交替。**在 safety.filter 之后执行**（唯一一条不许被过滤掉的指令）。阈值 1.0 s 的依据：正常最慢的一次（looming 转向逃逸的尾巴）是 0.75 s，不会被误触发。

数据（6 种子 ×60 s，同样场地/参数）：
- v15：碰撞 58 | 停顿 70.2 s（19.5%）| 50 次 | 最长 3.35 s | touching 1.2%
- 只修 geofence+推离：37.0 s / 24 次 / 最长 1.8 s
- + stall breaker：31.5 s / 17 次 / 最长 1.1 s
- + cruiseFloor 0.4：**4.9 s（1.4%）/ 0 次 ≥0.5 s / 碰撞 43**
- 浏览器端到端（v17，3 种子 ×45 s）：0 JS 错误，stallBreaks 1/局，pushes 2–5，peakAlt 1.09–1.38 m。

**方法论收获**：用户报"卡住/悬停"这类症状时，先写"症状探测器"（低速持续时长 + 同时刻的 touching/note/刹车/半径），不要凭直觉改碰撞代码——这次直觉（碰撞）完全错了，真凶是 geofence 和大脑刹车。另外 `AUTO_TUNE` 之外，`Safety`/`Decoder` 的默认值也在 autoplay 链路上，改前先看清哪些是 config 读入、哪些是代码默认。

### 协议要点（写文档时最容易讲错的三点）
1. **三个值是二补码有符号字节**：scale=120 时 -120 在线上是 **0x88**（= 256-120），不是带符号位单独的
   0x78。Python 发送 `int(v) & 0xFF`，接收 `b-256 if b>127 else b`。
2. **0xAA 本身也是合法值字节**（= -86）。所以接收端必须**按位置解 4 字节**，不能"找下一个 0xAA"当分隔符
   ——不然会同步到值字节上永远错位。只有载荷字节超出 -scale..scale（不可能）时才是假帧头，丢 1 字节重同步。
3. 协议**无校验、无高度、无心跳**：所以接收端**必须**自己实现 300 ms 无有效帧 → 收油门/降落。拔线后
   Python 这边什么都做不了，飞控的 RX-loss failsafe 才是真正的安全网。

### 实现中踩的坑（都已被测试锁住）
- `struct.pack('b', 200)` 抛 `struct.error`：改用位运算 `int(v) & 0xFF`，并补 `_from_int8`。
- **20 Hz 限速器因浮点边界丢一半帧**（200 tick 只发 100 帧是真实 bug）：`now - _last_tx < period`
  在循环"恰好"睡一个周期时会落在 49.999/50.001 边界。修法 `self.period - 1e-6`。这个是产品级 bug。
- `all(_from_int8(b) <= limit ...)` 忘了负下界：改成 `-limit <= _from_int8(b) <= limit`。
- CLI 把 serial 的 kwargs 传给了所有后端 → `SimDrone got unexpected keyword`：改成 `elif args.drone == "serial":` 分支。
- `takeoff()`/`land()`/`emergency_stop()` 走 20 Hz 限速器会让测试挂住：改为直接 `_send` + 短 sleep，
  且**最后写入线上的一定是 `AA 00 00 00`**。
- 测试里 fake clock：`_drone()` 辅助函数传 `clock` 并设 `d._last_tx = clock["t"] - d.period`；
  `takeoff()` 必须在装上假 `time.monotonic` **之后**调用（它自己会读真实时钟）。
- 沙箱里 `reg.exe` 被拦、`list_ports.comports()` 返回 0 → 没硬件可做真回环，改用文件/虚拟串口 + `FakeSerial`
  注入的接收端测试。**`--drone serial` 是唯一不需要 `--send` 就真写帧的后端（SERIAL TEST MODE）**。
